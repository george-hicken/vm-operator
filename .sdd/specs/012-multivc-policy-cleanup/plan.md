# Plan: multi-vCenter resource policy deletion fence

The shard controller registers the existing shared finalizer with a fresh API read, resource-version precondition, and conflict retry before any provider create/update. It rereads deletion state as part of registration and verifies the live gate before the provider call. If deletion has started, it performs no provider work. The shard deletion path returns an explicit unsupported error, leaves the shared finalizer in place, and does not call provider cleanup. Combined mode retains the prior path.

This is a bounded safety fence in the root Go module for the existing v1alpha6 API. It adds no CRD field, webhook, RBAC, or feature flag. The change is active only in `MultiVCModeShard`. The deferred patch excludes finalizers from shard metadata changes so a stale provider snapshot cannot restore or drop a gate. Unit tests cover persisted-before-create, an optimistic metadata conflict, and deletion racing creation; existing combined-mode unit and envtest cases cover its legacy behavior.

Historical folder and pool obligations have no durable per-SDDC record. Module and resource-pool status entries are incomplete as an obligation ledger, and the current SDDC roster cannot identify a removed historical SDDC. A prior normal reconcile can drop a removed Zone's pool status without deleting its vCenter child. Consequently, neither a first successful shard cleanup nor an empty status array proves global completion. Deletion remains pending by design; a later protocol needs complete historical participant/resource evidence or trusted creation provenance plus durable per-SDDC gates before external effects. Missing VC cannot be interpreted as cleanup success.

Confidence is high that this fence prevents the first shard from removing the only deletion gate. It does not establish complete policy lifecycle correctness. Revisit the design if the acceptance rollout deletes policies, if shard retirement is required, or if a complete obligation inventory becomes available. VM references created concurrently with deletion also require an explicit admission or ownership rule in the future deletion protocol.
